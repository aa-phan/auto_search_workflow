## Discretion choices made here (CONTEXT "Claude's Discretion")

- Identity layout `Board_Key, Chunk, Baselined_At, Count, IDs` (D-43). `Board_Key` is the job-key stem; `Chunk` starts at 1; `Baselined_At` is the completion marker, written only on a board's highest chunk with the stamp of the write that completed the set (lower chunks may keep an older stamp; readers use only the highest chunk's).
- Each ID is stored with a one-letter kind prefix (`b`/`f`/`s`, research Open Question 1): it keeps the disposition without extra rows, lets parity cross-check Identity against Tally, and keeps every cell text (no numeric reinterpretation of all-digit IDs). Rated costly, see Task 2.
- Growth is in place: new IDs extend the board's highest chunk until it would pass 40,000 characters, then a new chunk row is appended. Requests are budgeted by characters (1,000,000 per request, Google recommends at most 2 MB), never by the 2,000-row `APPEND_CHUNK`.
- Tally is one row per run with a JSON `Counts` cell (about 96 cells a day), not one row per run and dimension.
- Storage mode is read from the Discovery key `storage` (JSON `mode`); `compact` applies only when that key says so AND the `Events_Legacy` tab exists, otherwise the run writes as `dual` (the safe direction: everything still goes to Events). Plan 03-02 adds the rest of that key.
- Write failures: dual mode contains Identity/Tally failures (Events is authoritative, the next run repairs them, plan 03-02); compact mode lets an Identity failure stop the run before `save_boards` (rule 1 extended).
