## Discretion choices made here (CONTEXT "Claude's Discretion"; recorded in D-57 by Task 3)

- Parity state lives in one Discovery key `storage` (JSON: `mode`, `seeded_at`, `days` {UTC date: `runs`, `diff_runs`, `failed`, `admissions`}, `bar_met_at`, `last_check` {at, counted, declared, compared}, `last_diffs` (at most 10 strings), and the empty records `cutover`, `fold`, `restore` that later plans fill). No new Runs column (research Open Question 3): the run note carries the signal and `degraded_reason` reads it, as it does for `persistence`.
- The in-run check runs after the alert stage on the start-of-run snapshot (one-run lag, documented): it never delays a poll or an alert. The repair runs at run start because it is a cheap set difference and lets the observation write extend complete Identity rows.
- Minimum checked runs per UTC day = 12 of about 24 (research A7). A day counts only if it started after `seeded_at`. Admission = any checked run with `boards_activated` > 0 inside the three counted days. These are constants in `compact.py`; the owner can change them before the cutover.
- Declared (listed, not counted) classes: `unkeyable` (an identity-class key with fewer than three `|` segments: it stays in Events forever, so nothing is lost) and `duplicate_seen` (a key with more than one `seen` row: Tally and every report count first-seen rows only). Everything else is counted.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Discovery tab -> run_cycle | The `storage` JSON can be hand-edited or truncated in the Sheet |
| Identity / Tally tabs -> parity | Hand edits are untrusted input to the check |
| Run notes / Actions log -> public | The storage line and notes are public |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-07 | Tampering | `storage` key edited or truncated at 45,000 characters | medium | mitigate | `StorageState.load` is tolerant (fresh state on bad JSON, so the clock restarts and nothing is assumed met); pruning to 14 days and 10 listed differences keep it far below the cap (ClockTests) |
| T-03-08 | Repudiation | A crashed or skipped check reported as clean | medium | mitigate | An exception is the counted difference `check_failed`; a deadline skip is not recorded; days need 12 checked runs (ClockTests, PipelineDifferenceTests) |
| T-03-09 | Tampering | Identity or Tally edited so parity passes while detection breaks | high | mitigate | Layer 1 compares both directions plus kind, Count, marker and stem; layer 2 recounts Tally per run and dimension; dual-mode detection still reads Events (PipelineDifferenceTests) |
| T-03-10 | Information disclosure | Job text in the storage key, notes or log line | medium | mitigate | Diff refs are job keys, run ids, dimension keys or counter names; the log line prints counts; test asserts no title or URL substring in the stored JSON |
| T-03-11 | Denial of service | Check time or memory pushes a run past its timeout | medium | mitigate | Runs after the alert stage, skipped past 22 minutes of process time (not recorded); its seconds are in `last_check` and the log line for the live read in plan 03-05 |
| T-03-SC | Tampering | npm/pip/cargo installs | low | accept | No package is installed |
