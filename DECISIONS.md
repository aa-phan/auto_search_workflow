## D-02 New code lives in separate modules

`boards.py` (identity, list adapters, registry), `freshness.py` (dates, classes), `ledger.py` (events, derived state, retry selection), `eligibility.py` (deterministic gates), `state.py` (Sheet/CSV persistence for Boards/Events/Runs), `pipeline.py` (one run: discover, poll, detect, evaluate, deliver; all side effects injected so failure cases are testable). `hunter.py` stays the entry point and holds config, per-job hydration, Groq scoring, the user-facing Sheet/CSV stores and alerts. Reason: `hunter.py` is already ~1,400 lines; new concerns are pure and unit-testable in isolation.

## D-03 State persistence: append-only event ledger in the Google Sheet

Actions runners are ephemeral and the user must not touch Git. State goes in hidden Sheet tabs: `Events` (append-only), `Boards` (one row per board, rewritten atomically in a single request), `Runs`. Seen/evaluated/alerted are derived by replaying events, so a crash can never mark a later stage done. `Seen_Archive` is retired (superseded by `Events`; rejected jobs and reasons live there). Consequence: Sheets cell/row limits bound history; revisit pruning when `Events` exceeds ~200k rows.

## D-04 Freshness classes

(Window default changed from 4 to 12 hours: see D-17. The rules below are window-relative.)

See SPEC. Key choices: (a) source publication time beats observation; (b) update time is never publication; (c) Workable is day-precision, so it is `verified_fresh` only when the date is within the last day AND the board gap is within the window; (d) `observed_new` (no date) is not alerted: it is evidence of recency, not verification; (e) a ledger hit means no re-alert on republication.

## D-05 Baseline newly discovered boards

First successful poll records every existing ID as `baseline`. Exception: jobs whose source time proves they are within the window are still evaluated, because the date is authoritative. Otherwise a new board would flood the user with its entire backlog.

## D-06 Polling cadence

Hourly (`17 * * * *`, off-peak minute), 24/7. Serper runs inside the discovery cadence, not every poll, to conserve credits (superseded by D-18: rotating, budgeted at 10 credits per run, at most 20 a day). A poll gap is recorded, never assumed away; alerts older than the window are labelled by class instead of being sent as "fresh".

## D-07 Retry semantics

Transient failures write an `error` event and leave later stages undone. After 5 attempts a job is `abandoned` (recorded, not retried). Tracker append happens before the `evaluated` event and is guarded by a tracker-key check, so a retry cannot duplicate rows. Alerts are at-least-once.

## D-08 Filtering order

Keyword and exclusion checks on listing titles run before any fetch (most board jobs are irrelevant); deterministic hard rules run on the hydrated posting; Groq scores only what survives. Hard rules are conservative (reject only on clear signals); the LLM remains the judge of fit. (Level matching widened narrowly by D-25.)

`.env`, `Resume.pdf` and `resume.txt` are git-ignored. The resume lives in the Sheet (`Settings > Resume_Text`). `.env.example` could not be written in this environment (permission rule); its template is in the README.

## D-12 Identity: provider + region + identifier, casing per provider

Verified live: Lever and Workable APIs 404 on a re-cased slug; Greenhouse, Ashby, SmartRecruiters ignore case. So board keys keep case for Lever/Workable only. **Job keys are unchanged** (`ats|board-lowercase|id`; IDs are globally unique per provider), so every existing event and tracker row stays valid. `region` is part of the board and job key when non-empty; neither inventory has regional hosts and no regional adapter is added in this task.

## D-13 Validation semantics and provider policy

404/410 -> `invalid`; 200+jobs -> `valid`; 200+none -> `valid_empty` (Greenhouse, Lever, Ashby and Workable distinguish this from 404; SmartRecruiters does not); timeouts/5xx/429/non-JSON/adapter errors -> retried (1.5 s, 3 s backoff) then `transient`, with exponential re-try spacing across runs. A provider that fails 15 times in a row is paused for the run. Per-provider spacing (Lever 1 s, per its `Crawl-delay`). **SmartRecruiters' API host `robots.txt` says `Disallow: /` for generic agents**; we park its imported boards (`deferred`) unless the user sets `ALLOW_SMARTRECRUITERS_BULK=1`. Serper-found SmartRecruiters boards were originally exempt; D-19 removes that exemption.

## D-14 Activation budget (what is "monitored")

Importing ~22,000 boards must not become 22,000 hourly requests. Validated boards wait; the poller promotes the best-matching ones (most title-gate matches first) up to `Max_Active_Boards` (default 500) and `Max_New_Boards_Per_Run` (default 50). (Changed by D-19: Serper-discovered boards no longer skip validation and the budget.) Relevance is a snapshot, so a waiting board with nothing relevant today is re-validated weekly rather than polled hourly. (Changed by D-23: a monitored board's relevance is refreshed by every complete poll; and by D-26: promotion is pool-based and boards can leave monitoring.)

## D-15 Two writers, one registry

The importer (weekly/daily workflow) and the poller (hourly) can overlap. Registry writes are row-level upserts of only the rows a run changed, never a full rewrite, and each side owns different rows (importer: candidate/validated/invalid/deferred; poller: new/active/disabled). Each workflow has its own concurrency group so imports never delay polling. (Amended by D-28: the poller now also writes demotions into `validated` rows and makes every pool transition. Amended again by D-31: the two workflows now share one concurrency group and a writer lease; the guard the importer gained is best-effort, not an atomic compare-and-set.)

## D-16 Groq models (deviation from the original request, needs your OK)

`llama-3.3-70b-versatile` and `llama-3.1-8b-instant` return 404 `model_not_found` for this account today. Defaults are now `openai/gpt-oss-120b` (primary) and `openai/gpt-oss-20b` (fallback); both verified live on real postings; override with `GROQ_MODEL` / `GROQ_FALLBACK_MODEL`. ## D-17 Freshness window 4 h -> 12 h; discovery interval is a separate setting (deliberate SPEC change)

`Fresh_Window_Hours` defaults to 12 (was 4) everywhere it is used: classification, the first-poll baseline exception, the day-precision rule, alert eligibility, Settings defaults, docs, tests. `Discovery_Every_Hours` also defaults to 12 but is independent: neither setting reads the other. Hourly ATS polling is unchanged. The boundary is inclusive (12 h 0 s is inside). **Migration:** the old template wrote `Fresh_Window_Hours = 4` into every Sheet, so an old default cannot be told from a deliberate 4. The value is kept (explicit values always win) and flagged in the log and in `Runs.Notes` every run until the user changes it. Nothing rewrites the user's Settings tab. Environment `FRESH_WINDOW_HOURS=4` is flagged the same way. A wider window means more `verified_fresh` alerts per run and a longer tail of late-labelled ones, not more coverage.

## D-18 Scheduled discovery: rotating, budgeted, date-windowed; unfiltered search is manual only

(The search provider changed from Serper to Tavily in D-36; the rotation, budget-per-run and manual-only backfill rules below still hold, the Google-specific details do not.)

Evidence for the change: the unfiltered searches returned established boards (and ~29 of 30 stale jobs) and cost 2-3 pages per query on every run, while the public inventories already supply broad board coverage. Now: the slot list is ATS site x role x location; a persistent cursor (hidden `Discovery` tab) walks it; each run stops at `Discovery_Credit_Budget` credits (default 10) and each query at 2 consecutive no-gain pages or 3 pages. `SEARCH_TBS` cannot disable the window for scheduled runs (blank/`none` falls back to `qdr:d3` with a warning); the old unfiltered pass survives only as `--backfill` (boards only, own credit cap, never scheduled, does not move the cursor). Cursor moves after the found boards are saved and not at all when every request failed. Credits are counted as one per request; Serper's real billing is not verified here. Consequence: with defaults (6 sites x 7 roles x 8 locations = 336 slots, at most 10 queries per run, 2 runs/day) a full pass takes about 17 days at best and longer whenever a query pages. That is slow on purpose; the inventories carry the broad coverage and search only adds recent and unlisted boards.

## D-19 One admission path for every source

Inventory import, Serper results and manual seeds now share the same rules: identifier sanity and supported provider, `candidate` with provenance, provider policy (SmartRecruiters parked), validation, relevance-ordered promotion within `Max_Active_Boards` / `Max_New_Boards_Per_Run`. Serper boards used to become `new` (polled at once) without validation or budget; seeds likewise. Consequences: (a) a search-found board with nothing matching the user's titles waits (validated) instead of being polled; (b) a search-found board needs one extra validation request (bounded to 40 per run, the rest stay candidates for the validation job); (c) tests that seed a board now need a title that passes the gate (the default test fixtures do). SmartRecruiters jobs found by search are also not hydrated while the provider is parked (the per-job API is on the same disallowed host). **Existing data:** SmartRecruiters boards that Serper had already activated stay monitored (rows are never silently changed); the run notes count them so the user can decide. (Changed by D-27: they are now parked every run, history kept.)

## D-20 Search results are processed twice, independently

Board path: every result with a parsable board is submitted to admission, even if its job is seen, stale or excluded. Job path: only unseen identities whose title passes the cheap gate are hydrated (max 20 per run) for authoritative publication evidence; Google's date and the first observation are never publication. A temporary hydration failure is queued in the Discovery tab (max 60 jobs, 5 attempts, no credits) because rotation would not resurface the result for weeks; a closed posting is dropped. "Unique verified-fresh matches" = unique result jobs whose ledger state is `verified_fresh` and passed the title gate (whenever first observed).

## D-21 Pending deliveries are never discarded for age (reverses part of D-07)

D-07/ledger abandoned a retried alert once the job was more than 12 h past evaluation ("no longer fresh news"). That silently dropped alerts after any outage longer than half a day. Now a pending alert is retried until it is accepted (or, as before, rejected 5 times by Telegram); one delivered after the window carries "delivered late: published about N h ago (verified fresh when first seen)" in Telegram and the webhook. Scoring retries were never age-limited and still are not. The freshness class itself is not re-judged later.

## D-23 Board evidence from complete hourly polls (changes D-14; flagged conflict with "relevance is a snapshot")

Why: `relevant_jobs` was written only at validation, so a monitored board's count never changed again and nothing could show whether a board was still worth a slot. The hourly poll already downloads the whole listing, so refreshing costs no request. What changed: every **complete** successful poll refreshes `Relevant_Jobs` (unique posting IDs passing the title gate), `Eligible_Jobs` (relevant and not excluded by the US location rule, `eligibility.location_blocks`), `Relevance_At` and increments `Complete_Polls`. *Complete* = the fetch succeeded, was not turned into a failure by the suspicious-empty rule, and the adapter did not truncate the listing (`boards.Listing.complete`, False only when SmartRecruiters paging stopped at its 5,000-posting cap). A partial listing, a failed poll or a suspicious empty listing leaves all of these unchanged (new IDs on a partial listing are still observed and classified as before).

**Activity** (`New_Relevant_7d`, `New_Relevant_30d`, `Last_New_Relevant_At`) is computed from the ledger, never from search or update times: a *new relevant posting* is a `seen` job whose first observation came from a board poll, whose disposition is `pending` (it passed the title gate and was not stale), and whose observation pass was not a baseline (first poll or flood re-baseline) or a re-entry pass. Only observations at or after `Activity_Since` (the start of the current continuous monitoring stint) count. **Unknown is not zero:** both counts stay blank until the stint is 7 days old (`pools.ACTIVITY_MIN_DAYS`); after that a missing posting is a real 0. Open-job counts and activity are stored separately so an aggregator with many open jobs is not mistaken for an active board. The pass is recorded in the `seen` event (`pass: baseline | reentry`).

Consequences / limits: jobs first seen through Serper (not a board poll) are not activity; a legacy monitored board starts its history at its baseline time and shows unknown counts for its first 7 days; the observation window depends on polls actually succeeding. No LLM is used.

## D-24 Re-entry re-establishes the baseline (amends D-05 and SPEC "Baselining")

A board with status `new` and a recorded baseline can only be one that left monitoring and was promoted again. Treating its backlog as brand new would present every job added during the gap as just published; treating the whole gap as baseline would hide a genuinely fresh posting. So the first successful poll after re-entry uses the real board gap and source evidence only (`freshness.classify(..., reentry=True)`): time-precision date inside the window -> `verified_fresh`; dated but older -> `recent`/`stale`; future-dated -> `uncertain`; **undated while the gap is longer than the window -> `baseline`** (never `observed_new`). Already-seen IDs are not observed again, so pending evaluations and alert retries are untouched. The flood re-baseline rule is skipped for re-entry. Afterwards the board is `active`, `baselined_at` is reset and a new stint starts (`Activity_Since`, `Complete_Polls` 0, counts unknown). A failed re-entry poll keeps the board `new` and it re-enters on a later run.

## D-25 Title-gate audit: level matching (amends D-08 narrowly)

Finding (run against the default Settings): "Marketing Coordinator" already passes, because Coordinator is itself a configured level word. The rejected suitable titles were spelling variants of configured levels or levels written with a hyphen: "...Internship" (the whole-word match did not accept "Internship" for Intern), "Jr. ..." / "Jr ..." (not Junior), "Entry-Level ..." / "Marketing - Entry Level" and "New Grad ..." (not in the default levels at all). Titles with no level signal at all ("Content Creator", "Web Designer", "Social Media Marketing", "Marketing Strategist") stay rejected on purpose: the level word is the filter that keeps senior and unrelated roles out before any fetch. Changes: (1) inside a configured term a space and a hyphen are interchangeable; (2) when the user's `Target_Levels` contains Intern or Junior, "Internship" and "Jr"/"Jr." also match; (3) the default `Target_Levels` gains "Entry Level, New Grad" (existing Sheets keep their explicit value; only new Sheets and blank cells change). Seniority exclusions (Senior, Lead, Manager, ...) are checked first and unchanged ("Senior Marketing Internship" and "Marketing Lead - Entry Level" are still rejected). Cost: the manual `--backfill` and the rotation slot queries now carry two more level terms (backfill builds 4 queries instead of 2 for the default Settings, so spends more credits).

## D-26 Established and exploration pools with a weekly bounded rebalance (changes D-14; flagged conflict with vacancy-only promotion)

Problem shown by the data: promotion only filled vacancies, so the first ~500 qualifying boards kept their slots indefinitely, their relevance was never re-measured, and better boards could not enter. New policy, all counts configurable in Settings: `Max_Active_Boards` is split into an **established** pool (default 400) and an **exploration** pool (default 100, `Exploration_Share_Percent` 20). Every board admitted to monitoring enters exploration on a trial (`Exploration_Days`, default 7); boards never tried before go first, so a board without history has a fair route in (the first-trial order is most open eligible jobs). The monitored total never exceeds the cap through admission; exploration may exceed its target only while established has free slots, so no slot sits idle.

A weekly rebalance (`Rebalance_Every_Days`, default 7) is a pure decision over the recorded fields (`pools.plan_rebalance`): ended trials are compared with the weakest established boards by one documented score (D-30 lists the weights as initial choices); a trial graduates into a free established slot, or replaces an established board only if it scores more than 1.0 higher AND that board was the replacement target in two consecutive cycles; at most `Max_Replacements_Per_Rebalance` (20) established boards leave per cycle; trials still running are never touched; losing trials go back to the waiting list only as far as relevant boards are waiting; a lowered cap sheds the lowest scores first (established sheds count against the bound). **No demotion on thin evidence:** a decision needs `Exploration_Days x 12` complete polls, a successful last poll, evidence under 24 h old and a known activity count; boards without it are protected that cycle (their weak streak resets) and trials without it are extended. A demoted board returns to `validated` keeping validation, counts, baseline, last success, provenance and every ledger event (see D-24 for re-entry). Boards already monitored when pools are introduced are labelled exploration trials, so they earn established status by the same measurement, not by tenure.

Ships in **report mode** (`Rebalance_Mode` = `report`): the weekly plan is recorded (Discovery-tab keys `rebalance`, `rebalance_report`, `Runs.Rebalance`) but nobody moves until the setting is `on`; `python hunter.py --rebalance-report` previews it with nothing written. Consequence of report mode: weak streaks only advance when the plan is applied. Until trials end (7 days after the first run) pools only label boards.

## D-27 Monitored SmartRecruiters boards are parked (resolves the D-10 and D-22 open items; changes D-13 / D-19 "Existing data")

D-13/D-19 parked SmartRecruiters for every new admission but left boards that Serper had already activated polling a host whose `robots.txt` disallows generic crawlers. That was an inconsistent policy applied to old rows and new rows differently. Now `pools.sync_pools` runs every run before activation: any `new`/`active`/`disabled` board whose provider is blocked becomes `deferred` (validation `deferred`, last error = the policy text, `Pool_Reason` "parked ...; history kept"), with baseline, last success, counts, provenance and ledger events kept and the stint counters reset. Waiting (`validated`) SmartRecruiters boards are never promoted while the provider is blocked (`activate_waiting(blocked=...)`) and are parked by the validation job. `ALLOW_SMARTRECRUITERS_BULK=1` opts back in for new promotions; parked rows return through validation and re-enter with a re-established baseline (D-24). Reverting the code does not unpark rows (reversibility note in STATUS).

## D-28 Pool transitions are made only by the poller (amends D-15)

The hourly poller (never concurrent with itself or with the importer after D-31) is the only process that promotes, graduates, demotes, parks or relabels boards; the weekly rebalance is a step of an hourly run, not a new workflow. Demotion writes a `validated` row, which D-15 had assigned to the importer; the importer therefore no longer overwrites a row whose current status is `new`, `active` or `disabled` (a best-effort guard, NOT an atomic compare-and-set: `state.save_boards(..., skip_if_status=inventory.POLLER_OWNED)` re-reads the CURRENT status just before writing and drops rows a poller has taken; the CSV store does the same against its file). Corrected by D-31: the guard is defence in depth behind serialization, and a skipped row's provenance is merged rather than lost.

## D-29 Validation runs two independently budgeted queues

Problem shown by the data: one due list sorted by priority (boards both inventories vouch for first) and cut to `--max-validations` put roughly 18,500 never-validated candidates ahead of every re-check, so validated boards waiting for a slot were never refreshed (and relevance went stale). Now `inventory.run_validation` builds (1) candidates (status `candidate`, or `deferred` once the provider is allowed), ordered by the old priority, interleaved by provider, cut to `--max-validations`; and (2) re-checks (`validated` after 7 days, `invalid` after 30), ordered oldest-first by the timestamp they became due from (a missing timestamp first), interleaved by provider, cut to `--max-revalidations` (default 500; the workflow passes 2000). They are merged by strict alternation starting with a re-check, then whichever queue remains, so neither starves the other; waves, the time budget, the per-provider breaker and batched saves are unchanged. The summary and report show due counts, per-queue attempted counts and the age of the oldest waiting candidate / oldest overdue re-check. A due re-check refreshes `Relevant_Jobs`, `Eligible_Jobs` and `Relevance_At` of waiting boards (monitored boards are refreshed by their own polls instead).

## D-30 Open items to confirm (initial operating choices, not proven)

- **80/20 split (400 established / 100 exploration), 7-day trials, weekly rebalance, at most 20 replacements per cycle:** starting values chosen to make a trial long enough to see a week of activity and a replacement rate small enough to review. No data yet shows they are best; all are Settings (`Exploration_Share_Percent`, `Exploration_Days`, `Rebalance_Every_Days`, `Max_Replacements_Per_Rebalance`).
- **Score weights:** score = 2 x min(new relevant postings per week, 5) + min(open eligible jobs, 5); margin 1.0; two consecutive weak cycles before an established board leaves; `Exploration_Days x 12` complete polls (84 at the default) as the minimum evidence; evidence at most 24 h old. These are labelled initial choices, are not job scores, and were not tuned (AGENTS.md rule 7 is respected: the Groq job scorer and `Min_Alert_Score` are untouched).
- **`Rebalance_Mode` ships as `report`:** until you set it to `on`, the weekly rebalance only records its plan (Discovery-tab keys `rebalance`, `rebalance_report`, `Runs.Rebalance`) and nobody moves. Review `python hunter.py --rebalance-report` (or run the Job Hunter workflow with `rebalance_report` ticked) first, then set `Rebalance_Mode` to `on`. Pools themselves apply at once: boards are labelled, and trials start, in every mode.
- **Existing Sheets and `Target_Levels`:** the default now includes "Entry Level, New Grad" but an existing Sheet keeps its explicit value; add them in Settings if you want those titles.
- **Provenance of monitored boards:** the importer skips poller-owned rows (D-28), so a re-import cannot add a new source to a board that is currently monitored until it leaves monitoring.
- **Not counted as activity:** jobs first seen through Serper search; partial listings are only detected for SmartRecruiters past 5,000 postings (other adapters return the whole listing in one response).

## D-31 Serialized registry writers; the importer guard is not a compare-and-set (corrects D-28)

Trace of every writer of the shared state: the hourly poller (Boards, Events, Runs, Discovery, tracker), the inventory importer/validator (Boards, Inventory), manual `workflow_dispatch` runs of either workflow, and local `hunter.py` commands with Sheet credentials. D-28's "compare-and-set" re-read a row's status and then wrote: two operations, no atomicity, and Google Sheets has no conditional write. Fix, in order of strength: (1) both workflows now share the concurrency group `job-hunter-state` with `cancel-in-progress: false`: scheduled and manual runs queue, a running writer is never cancelled; GitHub keeps only the newest *waiting* run per group, so an hourly poll waiting behind a long import (capped at 40 min) can be replaced by the next hourly run (at most one poll delayed/skipped per import). (2) Every writing command takes an advisory lease (hidden `Lock` tab; `state/lock.json` for CSV, where exclusive-create IS atomic) with a TTL a little over each workflow's run limit (poller 30 min, inventory 45 min), waits up to `STATE_LEASE_WAIT_SECONDS` (default 300) and then exits 3 without writing; it never cancels the holder. A crashed holder cannot block longer than its TTL. (3) The importer's skip guard stays, and a skipped row's provenance/name are now merged into the stored row (`boards.merge_provenance`) instead of being dropped. **Remaining limits:** the Sheet lease is write-then-verify with a 3 s settle, not atomic; read-only commands and `--dry-run` take no lease (their one write is idempotent tab/header bootstrap); a local run against the production Sheet is serialized only if it uses the lease (every writing command does). Not verified against a real Sheet or on GitHub.

## D-32 Allocation correctness findings (confirmed by a multi-week simulation, `tests/test_allocation_correctness.py`)

Traced: 500 monitored boards migrate into exploration -> trials graduate into established vacancies -> losers return -> waiting boards enter. Progress works: the replacement cap bounds only established boards (`replace`/`shed`); graduation into a vacancy and returning losing trials are uncapped; weak streaks are recorded by every APPLIED plan whether or not a replacement happens (report mode records nothing). **Confirmed problems, fixed:** (a) *oscillation*: a loser with open jobs returned to the waiting list was counted as "waiting", justified returning the next loser and was re-admitted next hour once never-tried boards ran out (the supply of never-tried relevant boards is finite; the small samples taken so far cannot say how large it is, and nothing here shows that the cap cannot be filled), so the same boards were re-baselined weekly (trials reached 4 in 6 simulated weeks) -> boards that already had a stint are not waiting and not admitted for `2 x Exploration_Days` (`boards.cooling_down`; no clock = no cool-down). (b) *trials that can never be judged* (thin evidence: stale evidence, persistent partial listing, too few polls) were extended every week and the "no comparable established board" deferral had no bound -> a trial is rotated out once `3 x Exploration_Days` old (action `rotate`, reason says no verdict was reached; history kept; if nothing waits, it is extended again). (c) *slack trap*: a 7-day trial ends up to an hour before 7 stint-days exist, so its activity was "unknown" and the trial was extended a week -> a one-hour slack in the minimum observed time. **Dismissed:** the weekly cadence makes real trials 7-14 days (a trial admitted just after a rebalance waits for the next one): accepted and documented, not tuned. Established boards whose evidence is permanently unavailable are still never demoted (protected); only SmartRecruiters had a persistent partial listing and it is parked.

## D-36 Search provider: Serper -> Tavily (flagged: replaces D-18/D-35's Google mechanics; rotation, admission and freshness rules unchanged)

**Why it was feasible:** Tavily's current API reference (docs.tavily.com, read 2026-10-14) has `include_domains` (restrict to a domain, max 300), `start_date`/`end_date` (YYYY-MM-DD) and `time_range` (day/week/month/year), `search_depth` basic/fast/ultra-fast = 1 credit and advanced = 2, `max_results` 0-20, `include_answer` / `include_raw_content` (off by default), `include_usage`, and **no pagination parameter**. There is no `site:` operator and no `tbs`.

**Mapping.** ATS host -> `include_domains=[host]`; role -> query `"<role> job"`; three-day window -> `start_date = today - 3d` (no `end_date`; the manual backfill sends no date); mode `basic` (1 credit); `chunks_per_source=1`; answer, raw content, images and favicons off; `include_usage` on, so the credit cost is read from each response (documented price is the fallback). Search is no longer paginated: `DEFAULT_MAX_PAGES` is 1, one request per slot, up to 20 results. The engine keeps its generic stall/page logic but Tavily never uses it.

**Evidence for the parameter choices (live, boards.greenhouse.io, 7 default roles, ATS publication time read from each board's own list):** no window: 136 results, 19% of dated jobs published within 72 h, 77 of 130 job URLs no longer listed; `start_date` -3 d (basic): 80 results, **95%** within 72 h (median 40 h), 5 unlisted; `time_range=week`: 114 results, 66% within 72 h; `start_date` with `search_depth=fast`: 42 results, 0% within 72 h and 6 boards (cheaper modes are not better; `fast` is not used); `filter_by_published_date` / `include_published_date` return nothing for ATS pages (they carry no `published_date`), so they are not used. **The window is retrieval only:** in the 10-slot comparison below only 69% of returned job pages were published within 72 h and 10% within 12 h. ATS publication evidence stays authoritative for the 12-hour window; a Tavily `published_date` is stored on the hit but never read.

**Credits and the monthly ledger.** Persistent ledger in the Discovery tab (`search_budget`): per UTC month, `used`, `calls`, `by_path` (rotation / manual / backfill), `limit_hit`. One ledger for every search path; each request is charged as it is made, and the ledger is saved even if discovery fails midway or the run is a dry run. Cap default 1,000 (`Search_Monthly_Credits`, the free "Researcher" plan's allowance) with `Search_Reserve_Credits` 200 held back from scheduled runs: scheduled discovery stops at 800, `--discover` and `--backfill` may use the rest. The per-run cap (`Discovery_Credit_Budget`, 10) still applies; the default schedule uses 20 credits a day (about 600 a month). Exhausted -> discovery is skipped and noted, **polling continues**, and the run is not marked as a discovery run so it resumes by itself in the next month. A 432/433 stops the run and blocks spending (`limit_hit`) until the month changes or the account counter shows room. **What the local counter cannot observe:** requests from other keys, projects or hand-made calls (the free `GET /usage` is read before each discovery and the larger figure wins; a smaller plan limit lowers the cap), and Tavily's billing-cycle start day (undocumented in the API reference: the local count resets at the UTC month; a different cycle day is covered only by the account counter). Observed: `/usage` still reported 0 after about 55 credits had been spent (the counter appears to lag or aggregate slowly), so for now the response-reported credits are the only measured figure. Failed requests are not charged locally (Tavily's docs say failed requests are not billed for extract/map; for search this is assumed).

**Migration.** `TAVILY_API_KEY` replaces `SERPER_API_KEY` / `SEARCH_API_KEY` (workflow secret renamed; `SEARCH_WINDOW_DAYS` replaces `SEARCH_TBS`; `SEARCH_PAGES`, `SERPER_NUM`, the Google query builder, `scheduled_tbs` and the Serper client are deleted). **The old `.env` was not edited** (project rule): add `TAVILY_API_KEY` there; the obsolete `SEARCH_API_KEY` line is simply ignored. Rotation state written under Serper has no `provider` field and is **discarded: the rotation restarts at slot 0** (said in `Runs.Notes` once; the slot list is unchanged but the old cursor measured coverage of a different engine); `backfill_cursor` is new. The registry, ledger, job history and pending hydration retries are untouched. Rows and events written earlier keep `serper` as their provenance/source label (history is not rewritten); new rows use `tavily` (board provenance) and `search` (ledger source); readers accept all three. New Settings rows (`Search_Monthly_Credits`, `Search_Reserve_Credits`) are optional: older Sheets use the defaults.

**Quality comparison (same 10 slots, 10 credits each, same day; Serper with the D-35 query, Tavily as implemented):** Tavily 181 URLs, 156 boards, 69% of dated jobs within 72 h, 10% within 12 h, 27 jobs pass the title gate, 16 of them US-eligible; Serper 73 URLs, 65 boards, 68% / 9%, 15 pass the gate, 8 US-eligible; board overlap 54 shared, 102 only Tavily, 11 only Serper. Through the real pipeline (first Tavily run, rehearsal registry): 10 credits, 41 new unique boards, 51 eligible (validated or monitored; SmartRecruiters ones are parked), 9 promoted, 1 verified-fresh match, 3 jobs scored by Groq. **Counter labels:** `New_Unique_Boards` counts boards new to the registry, `Eligible_Boards` counts validated or monitored boards among ALL boards the results named (new or known), so eligible can exceed new; `Result_Boards`, `Result_Parked`, `Result_Invalid` and `Result_Awaiting_Validation` were added so the numbers reconcile (eligible + parked + invalid + awaiting = result boards). **Not claimed:** Tavily is not shown to cover everything Serper/Google covered (the 11 Serper-only boards), nor to guarantee freshness, and one day's comparison on 10 slots is a sample, not a benchmark; search results vary between calls.

## D-37 Deployment preparation: local production writes disabled, lease facts, backoff, completeness by documented behaviour

**Lease findings (tests/test_deployment.py).** (1) The first file-lease version (create the file, then write it) was **not** exclusive: 12 simultaneous acquirers produced 5 winners, because a reader saw the empty file, called it unreadable-therefore-expired and took over. It is now an exclusive `flock` held by the owner's file descriptor (kernel-arbitrated on one machine; released when the process dies; no expiry needed; verified with 12 threads and with a second process). (2) The **Google Sheet lease is not atomic and is not described as such**: it is write-then-verify, and the test shows an interleaving where a writer with a stale read also verifies its own token, so two writers believe they hold it. (3) A Sheet lease expires after its TTL (poller 30 min, inventory 45 min, both above their workflow timeouts of 25 and 40 min, asserted by a test); if a run outlives its lease, the end-of-run check logs an error and another writer may have entered. (4) Release is owner-only (a different token releases nothing). **Decision:** reliable exclusion between a local command and a scheduled run cannot be established on a Sheet, so **production writes happen only in the serialized GitHub workflows**: a local command that would write while `GOOGLE_SHEET_ID` is set refuses to run (exit 4) unless `GITHUB_ACTIONS=true` or `ALLOW_LOCAL_SHEET_WRITES=1` is set explicitly for a TEST Sheet no workflow writes. Read-only commands (`--dry-run`, `--url`, `--rebalance-report`, `--search-usage`, `--inventory-report`) are unaffected; local CSV state (no Sheet) is unaffected.

**Provider backoff.** HTTP 429 raises `BoardRateLimited(retry_after)` (a transient `BoardError`, never "closed"): the poller stops requesting that provider for the rest of the run (default 5 min, max 15), its other boards are `skipped` (not failures, state untouched, noted in `Runs.Notes`); validation extends the per-provider spacing. Workable's earlier 429s came from a burst of probes at 0.15 s spacing.

**Completeness by documented behaviour** (see SPEC "Board registry"): Greenhouse and Ashby unpaginated; SmartRecruiters `totalFound`; Lever continued with `skip` when the list length looks like a page size; Workable (undocumented widget) marked possibly truncated at such lengths; none requires a reported total.

**Repository hygiene.** `.gitignore` now also excludes `tracked_jobs*.csv` and `legacy/*.csv` (job-search data: scores and verdicts about the candidate); the three tracked copies are removed from the index (not deleted from disk). Git history contains no secrets (scanned for Tavily/Groq/Google/Telegram/GitHub token patterns and private keys: none) but still contains those CSVs; the repository is meant to be private.
