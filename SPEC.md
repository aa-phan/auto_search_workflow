# SPEC: Fresh-job alerts for a non-technical user

Status of this file: the contract. Change behavior only after changing (or flagging a conflict with) this file.

## Goal

Surface relevant jobs **within 12 hours of their publication** (`Fresh_Window_Hours`, default 12) to a non-technical user. Google Sheets is the only interface (settings in, tracker out). Telegram delivers push alerts for top matches.

## Honest limits (read before promising anything)

- Coverage = the ATS boards we have **discovered and can poll** (Greenhouse, Lever, Ashby, Workable, SmartRecruiters). Jobs on other ATSs, company-hosted pages, LinkedIn, Indeed, etc. are not covered.
- We **cannot guarantee** earlier or broader coverage than LinkedIn/Indeed. What we can state is conditional: **if** a board is monitored **and** a scheduled poll actually runs **and** its listing is complete, a posting on it is detected by that poll, and its freshness is labelled from the evidence. Scheduled runs are best-effort and a listing can be truncated (see below), so this is not an hourly guarantee.
- GitHub Actions schedules are best-effort: runs can start late or be skipped. The 12-hour target holds only while successful polls keep occurring; the system records actual gaps and labels late finds as not fresh.

## Loops

1. **Discovery loop** (Tavily web search; every `Discovery_Every_Hours`, default 12; a setting independent of the freshness window): a rotating set of searches restricted to one ATS domain and to the last 3 days (`start_date`) retrieves candidates. Unfiltered searches are never scheduled; they exist only as the explicit manual `--backfill`. See "Discovery".
2. **Polling loop** (hourly, 24/7 including nights and weekends): for every active board, list all current jobs from the ATS public API and detect job IDs we have not seen.

3. **Inventory loop** (weekly refresh + daily validation, separate workflow): two public company lists seed the same registry (see "Board registry"). It never scores or alerts.

The user never selects companies.

## Board registry

One persistent registry (hidden `Boards` tab) holds every board from every source: web-search discoveries (provenance `tavily`; `serper` on rows written before the migration), the `open-ats-feed` inventory, the `ats-scrapers` inventory, and manual seeds.

- **Identity:** provider + region/API host + board identifier. The default region is empty, so existing keys are unchanged. Casing follows the provider: Lever and Workable identifiers are case-sensitive (kept exactly); Greenhouse, Ashby and SmartRecruiters are not (compared lowercase, first-seen spelling used for API calls). Each unique board is polled once, however many sources list it.
- **Provenance:** every source that listed a board is recorded with its first-seen time; `Discovered_At` is the first time any source knew it; `Last_Validated_At` is the last time its adapter call succeeded.
- **Statuses:** `candidate` (imported, unvalidated) -> `validated` (exists; waiting for a monitoring slot) -> `new` (activated, not yet baselined) -> `active`. Also `invalid` (404/410), `deferred` (blocked by policy), `disabled` (monitored board that kept failing). Rows are never deleted, and an upstream list dropping a board changes nothing. Two transitions leave monitoring without deleting anything: a **demotion** (`active`/`new` -> `validated`, by the weekly rebalance, see "Polling budget") and a **policy parking** (`new`/`active`/`disabled` -> `deferred`, every run, see "Provider limits"). Both keep the board's baseline, last success, validation, counts, provenance and every ledger event; a board that leaves monitoring resets only its monitoring-stint counters (`Activity_Since`, `Complete_Polls`, activity counts). A `new` board that already has a baseline is **re-entering** monitoring (it was monitored before, left, and was promoted again): its next successful poll re-establishes the baseline (see "Baselining").
- **Board evidence (refreshed by every complete, successful hourly poll, from the listing already fetched; no LLM):** `Relevant_Jobs` (unique posting IDs passing the title gate), `Eligible_Jobs` (those whose listing location is not excluded by the US location rule), `Relevance_At`, `Last_Success_At`, `Complete_Polls`, and the activity fields `Last_New_Relevant_At`, `New_Relevant_7d`, `New_Relevant_30d`. A poll is *complete* when it succeeded, was not rejected as a suspicious empty listing, and the adapter has no sign of truncation. Completeness is judged by each endpoint's **documented pagination behaviour**, not by requiring a reported total: Greenhouse's list is unpaginated (a `meta.total` larger than the list is used as an extra check when present, never required); Ashby's posting API documents no pagination ("all currently published" postings; unlisted ones are skipped); SmartRecruiters pages with `limit`/`offset` and `totalFound` (paging that stops short is incomplete); Lever documents `skip`/`limit` but not the unpaged default (it returned the whole board live), so a list whose length is a typical page size (10, 20, 25, 50, 100, 200, 250, 500, 1000) is continued with `skip` until a short page; Workable's widget endpoint is undocumented (no pagination parameter is known), so a list of such a length is reported as possibly truncated, not assumed complete. **Provider backoff:** an HTTP 429 (Workable's, in practice) stops all further requests to that provider for its `Retry-After` (default 5 minutes, at most 15) for the rest of the run; its remaining boards are skipped without counting as failures and keep their state; during validation the provider's spacing is extended and the board is never read as closed. A partial listing, a failed poll or a suspicious empty listing changes none of these. Open-job counts and new-posting activity are separate facts.
- **New-posting activity** counts a first observation of a relevant job only when it is **evidence the posting appeared during the stint**: the source's own publication time/date proves it fresh (`verified_fresh`, which also counts a job first found by search, once, deduplicated by posting identity, `source` kept as provenance), or an undated job appeared on a board polled within the previous 6 hours (`observed_new`). Not counted: baseline and re-entry passes, `recent`/`uncertain`/`stale` jobs, and an undated job first seen after a longer gap (a *gap discovery*: we do not know when it appeared). Only observations at or after `Activity_Since` (the current monitoring stint) count.
- **Observation span and outages:** two complete polls more than 6 hours apart leave a hole; holes (and an outage still in progress) are stored in `Outages` for 30 days and are **not observed time**. The 7-day count is known only when the stint is at least 7 days (less 1 hour of slack) and at least 80% of that week was observed; the 30-day count only when at least 7 days of the 30-day window were observed, so a *partially observed* 30-day window gives a rate over the observed days (`New_Relevant_30d x 7 / observed days`), never over calendar days. A board that was unreadable shows unknown activity, not a real-looking zero. Residual bias: a dated job published during a hole and found right after it is counted without its hole being in the denominator.
- **Validation outcomes:** `valid` (jobs listed), `valid_empty` (exists, no jobs), `invalid` (404/410), `transient` (timeouts, 5xx, 429, bad payload: retried with backoff, never read as closed).
- **Validation runs two queues with their own budgets:** never-validated candidates (and parked ones whose provider became allowed), and overdue re-checks of `validated` (7 days) and `invalid` (30 days) boards. Re-checks run oldest-first and are merged with the candidates by strict alternation, so the ~18,500-board candidate backlog cannot starve the boards waiting for a slot. Waiting SmartRecruiters boards are parked while the provider is. Validation also records `Eligible_Jobs` and `Relevance_At`, and the moment a board began waiting (`Pool_Since`).
- **Imports are additive and idempotent:** re-importing an unchanged inventory writes nothing and never alters polling history, posting IDs, alert state or search discoveries. A failed or malformed download keeps the last-known-good copy.
- **Polling budget and pools:** only `new`/`active` boards are polled, at most `Max_Active_Boards` (default 500). That cap is split into an **established** pool (default 400) and an **exploration** pool (default 100; `Exploration_Share_Percent`, an initial operating choice, not a proven optimum). Validated boards are promoted by the poller (the same rule for every source), at most `Max_New_Boards_Per_Run` at a time and never beyond the cap. Every promoted board enters exploration on a trial of `Exploration_Days` (default 7). Boards **never tried before are admitted first** (the route in for a board with no observation history), then boards with the most open eligible jobs; a board with nothing open for the user's targets keeps waiting.
- **Weekly rebalance (transparent, bounded):** every `Rebalance_Every_Days` (default 7) the poller compares trials that have ended with the weakest established boards. Board score = 2 x min(new relevant postings per week, 5) + min(open eligible jobs, 5), from the evidence columns (rate per observed day, no tenure term, caps so aggregators cannot dominate). A trial graduates to established when established has a free slot, or replaces an established board only when it beats it by more than 1.0 and that board has been the weakest target in **two consecutive** cycles; at most `Max_Replacements_Per_Rebalance` (default 20) established boards leave per cycle; trials still running are never touched; a trial that loses returns to the waiting list only as far as boards are actually waiting, and **a board that left monitoring is not counted as waiting, nor offered a slot, for `2 x Exploration_Days` (14 days)**, so the same few boards cannot be re-baselined every week. A trial whose evidence stays too thin to judge is extended, but only until it is `3 x Exploration_Days` old: then it is **rotated out** (returned to the waiting list, history kept, no verdict about its hiring activity) if a relevant board is waiting for its slot, else extended again. **No board is demoted, shed or graduated on thin evidence:** a decision needs at least `Exploration_Days x 12` complete polls, a successful last poll, evidence refreshed within 24 hours and a known (7-day) activity count; one empty, partial or failed fetch can never be enough. A rebalance runs in **report mode by default** (`Rebalance_Mode`): it records the plan (hidden `Discovery` tab, keys `rebalance`, `rebalance_report`; `Runs.Rebalance`) and moves nobody until the setting is `on`. `python hunter.py --rebalance-report` prints the plan and writes nothing.
- **Transitions are made only by the hourly poller** (promotion, graduation, demotion, trial changes, policy parking). **Serialization:** every workflow that writes the registry (hourly Job Hunter, Board Inventory, scheduled or manually dispatched) shares one GitHub concurrency group (`job-hunter-state`, `cancel-in-progress: false`), so they run one at a time and a running job is never cancelled; and every writing `hunter.py` command (including local ones) takes an advisory **writer lease** (hidden `Lock` tab / `state/lock.json`, expires on its own) and refuses to start while another live lease exists. As defence in depth the validation workflow's save skips a row whose current status is `new`, `active` or `disabled` and merges its provenance into that row instead of dropping it. **Limits:** Google Sheets has no atomic conditional write, so the lease is write-then-verify (two processes starting within about 3 seconds of each other could in principle both proceed), GitHub keeps only the newest *waiting* run per group (an hourly poll waiting behind a long import can be replaced by the next hourly run), and read-only commands (`--rebalance-report`, `--url`) take no lease.
- **Baselining applies to imported boards exactly as to discovered ones:** the first poll records the existing jobs as `baseline` (not evaluated, no backfill); only a job whose source timestamp proves it fresh is evaluated.
- **Provider limits honoured:** Lever's `Crawl-delay: 1` is enforced; SmartRecruiters' API host disallows generic crawlers in `robots.txt`, so bulk validation of its imported boards is off by default (`ALLOW_SMARTRECRUITERS_BULK=1` opts in). SmartRecruiters also answers 200/empty for unknown companies, so its boards cannot be proven to exist. While the provider is parked (the default; the pilot runs with it unparked by explicit decision, D-38), **monitored SmartRecruiters boards are parked too, every run** (`deferred`, history kept, not polled) and parked or waiting ones are never promoted; opting in restores the old behavior for new promotions.

## Discovery (search is candidate retrieval only)

- **Rotation:** the slot list is every supported ATS site x role term (sites vary fastest). A slot's request is the query `<role> job` with `include_domains=[<host>]` (Tavily has no `site:` operator) and `start_date = today - 3 days`: location, level words and excluded-title words are NOT in the query (live probes of the previous provider returned 0 results with them, D-35) and are applied locally by the title gate, the US location rule and the scorer before/after hydration. A persistent cursor (hidden `Discovery` tab) selects the next slots each run; editing Settings changes the list and the cursor continues modulo the new length. A run in which every request failed does not advance the cursor. A cursor persisted for another provider (the Serper-era state has no `provider` field) is **discarded and the rotation restarts at slot 0** (D-36). The manual backfill walks the same slots on its own cursor (`backfill_cursor`) and never moves the scheduled one. A full cycle takes many runs by design.
- **Budget (per run and per month):** each run spends at most `Discovery_Credit_Budget` credits (default 10). Tavily's search is not paginated (no `page` parameter): one request per slot, at most 20 results, `search_depth=basic` (1 credit; `advanced` is 2, `fast`/`ultra-fast` also 1 but returned older and fewer results live), no generated answer, no content extraction. The actual cost is read from each response (`include_usage`). A **persistent monthly ledger** (hidden `Discovery` tab, key `search_budget`) counts credits per search path (`rotation`, `manual` = `--discover`, `backfill`); scheduled runs may use `Search_Monthly_Credits - Search_Reserve_Credits` (default 1,000 - 200 = 800), manual runs up to the full 1,000. When the allowance is exhausted, discovery is skipped (note in `Runs.Notes`) and hourly polling continues; discovery resumes by itself when the UTC month changes. Tavily's own counter (`GET /usage`, free) is read when available and the larger figure wins, so usage this application cannot see (other keys or projects, hand-made requests) still counts; it also lowers the cap if the plan limit is smaller. A 432/433 answer blocks all spending until the month rolls over or the account counter shows room. The local count restarts at the UTC calendar month; Tavily's billing-cycle start day is not documented in its API reference. `python hunter.py --search-usage` prints both counters. A dry run that searches still records the credits it spent.
- **Candidate retrieval only:** the 3-day filter is the search index's idea of a page's date, not when a job was published (live: about 69% of the returned job pages were published by the ATS within 72 hours, 10% within 12 hours; the rest were older), and a Tavily `published_date` is never used. Freshness comes from hydrating the posting at its ATS (source publication evidence, with the publication / republication / update / unknown distinctions above). Search-result dates and first observation are never publication time.
- **Two independent paths per result:** (1) its board identifier is submitted to board admission whether or not the job is seen, stale or excluded; (2) if the job identity is unseen and its title passes the cheap gate, it is hydrated and enters the normal evaluate/deliver pipeline. A temporary hydration failure is queued (bounded) and retried without spending credits.
- **Logging:** per query (identity, pages, credits, results, repeated, new boards, unseen jobs, stop reason) in the log and the hidden `Discovery` tab; per run in `Runs`: queries, pages, credits, repeated results, and the board counters below, plus unique verified-fresh matches.
- **Board counters (what the labels mean).** `Result_Boards` = unique boards the results named, **new or already known**. `New_Unique_Boards` = those the registry had never seen. So known = `Result_Boards` - `New_Unique_Boards`. `Eligible_Boards` = of the `Result_Boards`, those that are now validated or monitored (**new or known**: it can exceed `New_Unique_Boards`). The rest of `Result_Boards` is `Result_Parked` (provider policy), `Result_Invalid` (validation proved the board gone) and `Result_Awaiting_Validation` (candidates: inline validation is bounded per run or was transient). `Promoted_Boards` = of the `Result_Boards`, those admitted to monitoring this run; the run's `Boards_Activated` counts promotions from every source.
- **Coverage is not complete.** A 12-hour interval and a 12-hour window do not guarantee that everything inside the window is caught: indexing delay, a rotation that covers only part of the space per run, the 20-result cap per query and late or skipped scheduled runs all cause misses. Only jobs on polled boards carry the polling guarantee.

## Board admission (all sources)

Inventory imports, web-search results and manual seeds follow the same steps with the same functions (`merge_candidates`, `policy_blocks`, `validate_board` / `apply_validation`, `activate_waiting`). Search results and manual seeds run them inline per run (`inventory.admit_boards`); the importer runs them in batch (import, then the validation job): identifier sanity and supported provider -> registered as `candidate` with provenance -> provider policy (SmartRecruiters parked) -> validation through the ATS adapter (bounded inline for search/seed boards; the validation workflow handles the rest) -> prioritisation (most title-gate matches first) -> promotion only within `Max_Active_Boards` and `Max_New_Boards_Per_Run`. No source starts monitoring directly. A board already in the registry only gains provenance. Each unique board is polled once per run. Promotion enters the **exploration pool** on a trial (see "Board registry"). The importer's and validation job's writes are guarded: a row whose current status is `new`, `active` or `disabled` is never overwritten by them.

## Identity and dedupe

- Job identity = **ATS + board + posting ID**. Key: `ats|board(lowercase)|id`. URLs, hosts (`boards.` vs `job-boards.`), slugs and tracking parameters are not identity.
- Identity-bearing URL parameters are preserved when parsing (Greenhouse embed `for` and `token`, `gh_jid`). Tracking parameters (`utm_*`, `gh_src`, `lever-source`, ...) are ignored.

## Freshness vocabulary

| Term | Meaning |
|---|---|
| Source publication time | The ATS's creation/publish timestamp (Lever `createdAt`, Greenhouse `first_published`, Ashby `publishedAt`, Workable `published`, SmartRecruiters `releasedDate`). Precision is `time` or `day` (Workable is day-only). |
| First observation | When this system first saw the ID on a poll or search. |
| Update | The source's last-modified field changed (e.g. Greenhouse `updated_at`). Never treated as publication. |
| Republication | The source publication time moved later for a known ID, or an ID reappeared after absence. Logged; the job is not re-alerted. |
| Board gap | Time since the board's previous successful poll. A new ID on a baselined board was not visible at that earlier poll. |

Freshness classes (assigned once, at first observation, with the evidence recorded):

| Class | Rule | Alert? |
|---|---|---|
| `verified_fresh` | Time-precision source publication age <= `Fresh_Window_Hours` (default 12; the boundary itself counts as inside); or day-precision date within the last day AND the board gap <= window. | Yes |
| `observed_new` | No source date; new ID on a baselined board with gap <= window. Age unverified. | No (tracker only) |
| `recent` | Source date known, older than the window, within `Max_Job_Age_Days`. | No (tracker only) |
| `uncertain` | No source date and no usable board gap (e.g. search-only). | No (tracker only) |
| `stale` | Source date older than `Max_Job_Age_Days`. | No, not evaluated |
| `baseline` | Already on a board when it was first polled. Not treated as new. | No, not evaluated |

**Baselining:** the first successful poll of a newly admitted board records all existing IDs as `baseline`; only jobs whose time-precision source publication time is inside the window are evaluated. Day-precision dates cannot prove a 12-hour window on a first poll, so those stay `baseline`.

**Re-entry:** when a board that left monitoring is promoted again, its next successful poll is a re-entry pass. Already-seen IDs stay as they are (no new `seen` event). For an unseen ID the real board gap applies: a job with a time-precision source date inside the window is `verified_fresh` (alertable); a dated job outside the window is `recent` or `stale` as usual (a future date is `uncertain`); an **undated** job is `baseline` when the gap is longer than the window ("appeared while the board was not monitored; no source date"), never `observed_new` or `verified_fresh`. The pass then re-establishes the baseline and starts a new monitoring stint; re-entry observations are not new-posting activity.

## State model (separate, individually retryable)

- **Seen**: first observation recorded (with class and evidence).
- **Evaluated**: gates and scoring completed; outcome stored.
- **Alerted**: Telegram message accepted by the API.

A failure at one stage never marks later stages done. These stages belong to the job's ledger, not to its board: a pending evaluation or alert retry survives the board being demoted, parked or disabled. Transient failures (timeouts, 5xx, 429, Groq outage, Sheets/Telegram errors) are retried on later runs; rejected requests and permanent-looking failures are bounded at 5 attempts, then abandoned with a recorded reason. **A pending retry is never dropped because its job aged past the window**: the freshness class was verified at first observation and stays; an alert delivered after the window is labelled "delivered late". Delivery is at-least-once (a duplicate alert is possible if the process dies between sending and recording).

## Filtering order

1. Cheap checks on listing data (before any fetch): roles keyword in title, level keyword in title, excluded title words, freshness class. A space and a hyphen are interchangeable inside a configured term ("Entry Level" matches "Entry-Level"), and when `Target_Levels` contains Intern or Junior, "Internship" and "Jr"/"Jr." also match. A level keyword is still required; seniority exclusions are checked first and unchanged.
2. Hydrate the full posting from the ATS (authoritative date, location, text).
3. Hard eligibility rules (deterministic): age, excluded title (full), non-US location, minimum experience >= 4 years, required foreign language.
4. Resume-fit scoring (Groq) only for postings that pass 1-3.

## Delivery

- **Job Tracker** tab (visible): jobs scoring >= 50; `To Apply` (>= `Min_Alert_Score`) or `Stretch / Review`; columns include `Freshness` and `Source`. Append-only; user edits to `My_Status` / `User_Notes` are never overwritten.
- **Telegram**: one message per `verified_fresh` job scoring >= `Min_Alert_Score`, with title, company, location, score, verdict, gaps, apply link, tracker link.
- Hidden tabs hold internal state: `Boards`, `Events` (append-only ledger), `Runs`, `Discovery` (rotation cursor, hydration retry queue, last run's queries).

## Observability

Each run appends a `Runs` row: boards polled/failed, new jobs by class, alerts sent/failed, gap since the previous run, worst board gap, max alert lag. The Runs row also records pool membership (`Pool_Established`, `Pool_Exploration`), the relevant waiting list (`Waiting_Relevant`, `Oldest_Waiting_Hours`), `Relevant_Coverage_Pct` (monitored boards with open relevant jobs as a share of those plus the relevant boards still waiting), `Graduated`, `Demoted`, `Parked_Policy` and `Rebalance` (blank = not due, `report`, `applied`); every pool transition is logged with its reason. Per-board `Last_Success_At` is kept in `Boards`, together with its evidence columns (`Eligible_Jobs`, `Relevance_At`, `Activity_Since`, `Complete_Polls`, `Last_New_Relevant_At`, `New_Relevant_7d`, `New_Relevant_30d`) and its pool state (`Pool`, `Pool_Since`, `Trial_Until`, `Trials`, `Weak_Streak`, `Pool_Reason`). Older rows without these columns load with unknown evidence (blank, never 0).

## Pilot measurements and deployment (D-37)

- `python hunter.py --pilot-report [DAYS]` (read only, also a workflow input) reports, from the Runs log, the Events ledger, the Boards registry, the Discovery tab and the tracker: polling gaps and late runs, runs by trigger (`schedule` vs `workflow_dispatch`: only scheduled runs prove the schedule), relevant fresh jobs by source (title gate passed, source timestamp inside the window; baseline-pass jobs listed separately), publication-to-first-seen and publication-to-alert latency, late and duplicate alerts, pending failures, search credits (local counter) and board coverage, and the user's `My_Feedback` labels. It also carries a **limits audit** measured per run (columns `Duration_S`, `Load_S`, `Discovery_S`, `Poll_S`, `Evaluate_S`, `Events_Rows`, `Boards_Rows`, `Sheets_Reads`, `Sheets_Writes`, `Sheets_429`, `ATS_Requests`, `ATS_429`, `ATS_Seconds`, `Groq_Calls`, `Groq_429` in the Runs tab): run duration against the 25-minute timeout, time by phase, poll seconds per monitored board and a labelled straight-line projection to the board cap, Google Sheets requests per run against its quota (about 60 reads a minute per user) and retried rejections, ATS and Groq request counts and 429s, and the growth of the Events and Boards tabs against the 10,000,000-cell sheet limit. The report also has a **re-check flips** section: of the boards that were already validated and are checked again, how many gained (or lost) their relevant open jobs between two checks and how many days each had gone unchecked (cumulative statistics in the Discovery tab, key `revalidation_stats`, written by the validation run). It quantifies how many boards the 7-day re-check interval brings in late. It adds no gate or score.
- Job Tracker has a user-owned `My_Feedback` column (Would apply / Maybe / Irrelevant). Like `My_Status` and `User_Notes` it is never written or overwritten by the program; an older tracker gets only its header cell.
- `python hunter.py --delivery-test --to <chat id>` sends ONE synthetic, clearly labelled fixture through scoring -> tracker -> Telegram. It is isolated (no ledger event, no board row, a non-ATS URL) and validates the delivery plumbing only, never real-job quality.
- Production writes run only in the serialized GitHub workflows; local commands that would write to a Sheet are refused unless explicitly allowed for a test Sheet (D-37). The workflows are read-only toward the repository.

## Out of scope for now

Tuning scores, additional ATSs, non-US markets, email/SMS, a web UI, guaranteeing parity with job boards.

## Acceptance (smallest complete path)

Board poll -> new-ID detection -> keyword/eligibility gates -> scoring -> Sheet row -> Telegram alert, with: baselining proven, freshness class correct per evidence, retries proven for scoring and alert failures, polling gaps recorded. Live verification of Sheets, Groq and Telegram requires the user's credentials; until then they are reported as mocked-only.
